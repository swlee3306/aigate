## 2. 현재 코드 사실 (2026-11-09 확인, 구현자 조사)

| 영역 | 사실 |
|---|---|
| 제출 | `POST /api/v1/tasks`(쓰기 등급). 필드 `repo, base, prompt, class, agent`. 프롬프트 ≤64 KiB, `agent`∈{claude,codex}, `class`는 정규식 `^[a-z0-9_가-힣-]{1,32}$`만 검사한다(**정책의 종류 목록과 대조하지 않음**). `Idempotency-Key` 지원(24시간). 프롬프트는 ssh 강제 명령의 **stdin**으로 agent-vm에 전달된다 |
| 취소·재시도 | `POST /tasks/{id}/cancel`, `/retry`. 재시도 가능 조건은 `failed` + 인프라 실패 + 재개 가능 단계 + 3회 미만. 오류 코드가 `not_found/conflict/bad_request`뿐이라 사유는 메시지 문자열로만 구분된다. 취소가 경쟁에서 5번 지면 `ErrStateMismatch`가 **500**으로 나간다 |
| 웹 | 쓰기는 승인(grant)과 로그인뿐. 제출·취소·재시도·`/ops`·`/policy`·`/projects`를 호출하지 않는다. 입력 폼 화면이 없다. `api.js`의 `post()`는 추가 헤더를 못 보내 `Idempotency-Key`를 못 쓴다 |
| 서버 상태 | `GET /api/v1/ops`는 빌드·정책 해시·마지막 복원·캐시 개수만 준다(VM·쿼터 없음). 쿼터 조회(`openstack quota show --usage -f json`)는 허용 목록에 있지만 vm 패키지 안에서만 쓰이고 API 핸들러가 닿지 못한다. 클라우드 호출은 건당 수 초 |
| 기록 | `task_events`에 주체 열이 없다. 제출은 SQLite 이벤트만(원장 이벤트 없음). 취소·재시도의 원장 `task_transition`에도 주체가 없다. `approval_granted`만 `signer`와 `via`(주체 **종류**만)를 남긴다 |
| 게시 | `orch/<작업ID>` 브랜치를 ssh 원격으로 push. **MR 생성 코드(`draft_pr`)는 이미 있지만 https GitLab만 허용**(`checkAPIBase`). 이 GitLab은 http라 못 쓴다. 응답 본문을 버려 **MR 주소가 어디에도 저장되지 않는다**. 작업 기록과 `TaskView`에 브랜치·MR·원격 필드가 없다 |
| 비밀 | orchd는 ssh 키들·배포 키·GitLab 토큰 파일(`--gitlab-token-file`)을 플래그 경로로 읽는다. LLM·외부 API 호출 코드는 **저장소에 없다**(AI는 agent-vm의 `claude`/`codex` CLI뿐) |
| 저장소 | 스키마 버전 6. 프로젝트·게시 결과·MR 테이블 없음 |

## 3. W2a 설계

### 3.1 작업 제출 화면 (`#/new`)
- 필드: **저장소**(드롭다운), **기준 커밋(base)**(기본은 저장소의 현재 HEAD, 직접 입력 가능), **종류**(정책의 종류 목록에서 선택), **에이전트**(claude/codex), **요구사항 작성기**.
- 저장소 목록·HEAD·브랜치는 새 읽기 API `GET /api/v1/repos`가 준다: 허용 루트(`--allow-repo`) 아래의 git 저장소와 각 HEAD SHA, 최근 브랜치. 읽기 전용 git 호출만 한다.
- **종류는 제출 때 정책과 대조한다(제안).** 모르는 종류는 400(`unknown_class`). 지금은 정규식만 맞으면 받아들이고 검증·게시 단계에서야 효과가 나온다(2장).
- **요구사항 작성기(AI 없음):** 칸 네 개 — 목표, 수정 범위(고치거나 추가할 파일·디렉터리), 완료 조건(검증 기준), 하지 말 것. 서버가 아니라 **브라우저가 고정 템플릿으로 프롬프트를 조립**하고, 조립된 최종 프롬프트를 화면에 그대로 보여 준 뒤 제출한다. 최종 프롬프트는 **읽기 전용**이고 고치려면 네 칸을 고친다(그래야 "보이는 값 = 보내는 값"이 구조적으로 보장된다. 구현 후 정정, 결정 R9). 제출 API는 지금 그대로 `prompt` 문자열 하나를 받는다. 프롬프트 상한 64 KiB는 서버가 지킨다. AI 다듬기(W2b)는 이 칸들을 채워 주는 기능으로 얹힌다.
- 중복 제출 방지: 폼을 열 때 무작위 `Idempotency-Key`를 만들어 함께 보낸다(`api.js`에 헤더 옵션 추가).
- 큐 상한 **(구현 후 정정, 결정 R11/R12)**: 한 번에 대기(`queued`)할 수 있는 작업은 **주체(principal)별 20개**(`--queue-limit`)이고, 따로 **서버 전체 상한 100개**(`--queue-limit-total`)가 있다. 주체는 작업을 만든 요청의 actor(`kind:id`)이며, 작업의 가장 이른 `created` 이벤트의 `actor`로 센다(스키마 변경 없음). 넘으면 429(`queue_full`)이고 코드는 같고 고정 문장만 다르다: 주체별 "내 대기 작업이 가득 찼습니다", 전체 "서버 대기열이 가득 찼습니다"(주체·개수는 문장에 넣지 않는다). 두 검사와 삽입은 한 즉시(immediate) 트랜잭션이다. `system` 주체와 v7 이전(만든 이벤트에 `actor` 없음) 작업은 어느 주체의 한도에도 들지 않고 전체 수에만 센다. 전체 상한이 주체별 상한보다 작으면 시작을 거부한다. 한 세션이 큐를 독점하지 못하게 하되(전역 20개일 때는 가능했다), 탈취된 세션이 쓸 수 있는 양을 주체당 20개로 제한한다. 웹은 서버의 고정 문장을 텍스트로 보여 준다. 한 사람이 패스키 세션과 ssh 토큰을 함께 쓰면 버킷이 둘(`session:<id>`, `token:<id>`)이므로 사람당 실효 상한은 주체별 상한의 배수가 될 수 있다(설계상 의도, R6/R12).

### 3.2 취소·재시도
- 작업 상세 화면에 **취소**, **재시도** 버튼. 누르면 확인 창에 영향("진행 중인 단계는 끝난 뒤 결과가 버려집니다" 등)을 쓴다.
- `TaskView`에 `cancellable`(불리언)을 추가한다(`retryable`은 이미 있음). 웹이 상태 목록을 따로 들고 있지 않게 한다.
- 오류 코드를 정리한다(제안): 취소 — `already_final`(409); 재시도 — `not_retryable`(409, 사유 문구는 서버 문장 그대로 `reason` 필드), `state_changed`(409). **취소의 5회 경쟁 패배는 500이 아니라 409 `state_changed`**로 바꾼다(2장의 버그).
- 둘 다 쓰기 등급(세션은 CSRF). 서명은 요구하지 않는다(승인만 서명).

### 3.3 서버 상태와 진행 표시
- `GET /api/v1/ops`를 확장한다: `cloud` 블록에 쿼터(gigabytes·volumes의 한도/사용/예약), 테스트 VM 상태, 복원 볼륨 개수, 최근 복원 기록(최대 N건). 읽기 전용이다.
- **호출 비용을 숨기는 방식(제안):** orchd가 60초 TTL 캐시와 중복 호출 합치기(single-flight)로 한 번만 클라우드를 부른다. 실패하면 `cloud:{ok:false, code}`(고정 코드, 오류 원문 없음)로 응답하고 나머지 필드는 그대로 준다. `/ops`는 클라우드 블록을 최대 6초만 기다리고(느리면 `cloud_timeout`, 갱신은 뒤에서 계속된다), `test_vm.status`는 서버를 읽지 못했지만 쿼터는 읽은 경우(예: 복원 실패로 서버가 지워진 뒤) `ok:true`와 함께 `"unknown"`일 수 있으므로 웹이 이 상태를 표시해야 한다. 허용 목록의 읽기 동사(`quota show --usage -f json`, `server show`, `volume list`)만 쓰고 쓰기 동사는 추가하지 않는다.
- `OpenStackCLI`는 vm 패키지 안에만 있으므로 `Ops`와 같은 방식의 공급 함수(`CloudStatus func(ctx) CloudView`)를 데몬 설정에 추가한다.
- 화면: `#/ops`(서버 상태). 쿼터가 임계(예: 80%)를 넘으면 경고 문구와 정리 스크립트 안내(`cleanup-restore-volumes.sh`)를 보여 준다. 가장 흔한 고장(쿼터 초과로 복원 실패, docs/10 5장)을 미리 알리는 것이 목적이다.
- 진행 표시: 작업 상세의 타임라인에 **현재 진행 중인 단계와 경과 시간**을 추가한다(데이터는 이미 이벤트에 있다). 폴링은 기존 `poll`을 쓴다(실시간 푸시는 하지 않는다).

### 3.4 누가 했는지 기록 (스키마 v7)
- `task_events`에 `actor TEXT`(NULL 허용)를 추가한다. 값은 `kind:id` 형식: `session:mac-passkey`, `token:mac-ssh`, `socket:uid:1000`, 시스템이 한 전이는 `system`.
- 주체를 전달하는 방법(제안): API 핸들러가 `Principal`을 요청 컨텍스트에서 꺼내 `store`/`machine` 호출의 컨텍스트에 실어 보내고, 이벤트를 쓰는 쪽이 읽는다. 함수 시그니처(주체 인자 추가)는 바꾸지 않는다. 컨텍스트에 없으면 `system`.
- 원장: 제출에 `task_submitted` 이벤트를 새로 쓰고(지금은 원장 이벤트가 없다), 취소·재시도의 `task_transition` 페이로드에 `actor`, `via`를 추가한다. `approval_granted`의 `via`도 종류만이 아니라 `kind:id`로 통일한다.
- 기존 이벤트는 그대로(`actor`=NULL = 기록 이전). 마이그레이션은 열 추가뿐이라 되돌림이 단순하다(옛 orchd는 새 DB를 열지 않으므로 롤백에는 DB 백업 복원이 필요, W1과 같다).

## 4. W2b 설계

### 4.1 비밀 서비스 `orch-broker`
- 별도 systemd 서비스(`orch-broker.service`), 전용 계정 `orch-broker`. 키 파일은 `/etc/orch-broker/`(root 소유, `orch-broker`만 읽기)에 둔다: `openai.key`, `gitlab.token`. **`orch` 계정은 읽지 못한다.**
- 설정 파일 `/etc/orch-broker/broker.json`(root 소유, 수정은 sudo): 모델 ID와 **모델 단가**(입력·출력 100만 토큰당 USD), 입력·출력 상한, 시간당 호출 상한, **주당 비용 상한(USD)**, **AI에 코드를 보내도 되는 저장소 목록**, GitLab 기준 주소(정확히 한 개로 고정), 저장소→GitLab 프로젝트 매핑, MR 대상 브랜치.
- 통신: `/run/orch-broker/broker.sock`(그룹 `orch`가 접속 가능). `orchd`만이 아니라 같은 그룹의 모든 프로세스가 접속할 수 있다. 그래서 서비스는 **두 가지 일만, 입력을 엄격히 검사하고, 상한을 걸고** 받는다:
  - `refine`: 요구사항 글과 컨텍스트 → 구조화된 요구사항(JSON)
  - `create_mr`: 저장소, 원본 브랜치 `orch/<n>`, 제목, 설명 → MR 번호와 주소
- 남는 위험(숨기지 않음): `orch` 계정을 잡은 공격자도 이 두 일은 요청할 수 있다. **키는 읽을 수 없고**, 할 수 있는 일은 고정된 두 가지이며 상한이 걸려 있다. 키 유출과 임의 호출은 막지만, 허용된 범위 안의 남용(요금, MR 스팸)은 상한으로만 줄인다.
- 키는 이 용도 전용으로 새로 만들고, API 쪽에 사용 한도를 건다(사용자 작업, 런북에 포함).

### 4.2 AI 다듬기 흐름
> **정정 v0.2 (2026-11-09, 사용자 확인):** 처음 설계는 AI가 "네 칸을 채워 주는 것"으로 좁게 적었다. 사용자가 원하는 것은 **한 줄만 넣으면 AI가 계획서를 만들고, 요구사항 항목마다 체크박스로 구현 여부를 고르고, 추가 의견을 줄 수 있는 것**이다(시나리오 3~4단계의 "수정·제외·체크 방식 검토"의 첫 조각). 이 절을 그 흐름으로 바꾼다. W2a의 네 칸 작성기(`#/new`)는 AI 없이 직접 적는 용도로 남긴다.

1. 사용자가 저장소를 고르고 **한 줄**(또는 거친 글)을 쓴다.
2. 웹이 `POST /api/v1/refine/preview`로 **전송될 내용**(파일 목록, 크기, 제외된 파일과 이유, 총 크기)을 요청한다. orchd가 규칙에 따라 컨텍스트를 모으지만 **아직 아무것도 보내지 않는다**.
3. 사용자가 미리보기를 확인하고 `POST /api/v1/refine`을 누르면 orchd가 브로커에 보낸다.
4. 결과는 **계획서**로 돌아온다(검증된 JSON 스키마): 한 문단의 **목표 요약**, **요구사항 항목 목록**(항목마다 짧은 제목, 설명, 선택적으로 관련 파일), **확인이 필요한 질문** 목록, **범위 밖으로 둔 것** 목록.
5. 화면은 계획서를 **체크리스트**로 보여 준다. 항목은 **기본이 체크**된 상태다. **체크 = 이번에 구현, 체크 해제 = 구현 안 함.** 항목의 제목·설명을 고치거나 항목을 직접 추가할 수 있고, 항목마다 **의견**과 계획서 전체에 대한 **추가 의견** 칸이 있다. 질문에는 답을 적을 수 있다.
6. 사용자가 "확정"을 누르면 **체크된 항목 + 의견 + 질문 답**으로 요청 문장이 조립되어 **작업 하나**로 제출된다(결정 2026-11-09: 항목마다 작업을 나누지 않는다. 쪼개기는 W5). 조립된 최종 문장은 W2a와 같이 읽기 전용으로 보여 주고(보이는 값 = 보내는 값), 제출 경로와 큐 상한·멱등 키는 W2a 그대로다. 체크 해제된 항목은 요청에 **"하지 마라" 목록으로 넣는다**(에이전트가 임의로 구현하지 못하게 한다. 이 규칙은 결과 문서에서 시험으로 고정한다).
7. 체크리스트의 상태(어떤 항목이 체크됐는지, 고친 글, 의견)는 **브라우저 메모리에만** 둔다(저장소·쿠키에 두지 않는다). 새로고침하면 계획서 생성을 다시 해야 한다(비용이 들므로 확정 전 이탈 경고를 둔다).
- **컨텍스트 규칙(제안):** 저장소의 허용 목록 포함 여부는 **브로커의 root 소유 설정**이 정한다(`orch`가 바꿀 수 없음). 기본은 비어 있어 **어떤 저장소도 보내지 않는다.** 보낼 파일: 파일 목록, README, 요구사항 글의 키워드와 매칭되는 파일(개수·크기 상한). 저장소가 작으면(HEAD 트리 항목 40개 이하이고 크기 합계 240 KiB 이하) 나머지 모든 파일도 후보이며 미리보기에 `small_repo`("작은 저장소: 전체 파일")로 표시된다. 제외 규칙은 그대로 적용된다. 제외: `.env`, 키·인증서 파일, `*secret*`, `*credential*` 이름, 이진 파일, 큰 파일, `.git`. 제외는 orchd가 한 번, 브로커가 한 번 더 한다(이중 방어).
- **프롬프트 주입 대응:** 요구사항 글과 저장소 코드에는 AI를 속이는 문구가 있을 수 있다. 그래서 (a) 결과는 **JSON 스키마를 검증**하고 텍스트로만 표시하며(`el()`), (b) 어떤 결과도 **자동으로 제출·실행하지 않는다**(사용자가 항목을 확인·체크한 뒤 직접 "확정"), (c) 제출된 프롬프트는 기존 에이전트 격리(agent-vm, 강제 명령)에서 실행된다.
- **비용·기록:** 호출마다 원장 `refine` 이벤트(주체, 저장소, 전송 파일 수·바이트, 토큰 사용량, 성공 여부). **내용은 기록하지 않는다.** **주당 비용 상한(최근 7일 합계)**을 넘으면 `budget_exceeded`. 비용은 설정의 단가와 응답의 실제 사용량으로 계산하고, 호출 전에 최악 비용을 예약해 동시 요청이 함께 넘지 못하게 한다(구현 후 정정, 구현 계획 D2b).
- **외부로 나가는 데이터:** 요구사항과 선택된 코드가 **OpenAI API**로 나간다(요청에는 OpenAI가 응답을 저장하지 않게 하는 옵션을 넣는다). 사용자가 **어떤 저장소든 보내도 된다고 결정했다**(2026-11-09, `sample-app` 포함). 그래도 허용 목록 장치는 유지한다: 브로커의 root 소유 설정이 정한 저장소만 나간다.

### 4.3 MR 자동 생성
- 게시가 성공해 작업이 `done`이 되면 orchd가 브로커의 `create_mr`를 호출한다. 실패해도 **작업은 `done`을 유지**한다(코드는 이미 push됨). 실패는 이벤트와 화면 안내로 알리고 수동 재시도 버튼을 둔다.
- 기존 `draft_pr` 게시 동작은 건드리지 않는다. `checkAPIBase`(https만 허용)는 완화하지 않는다. MR 생성은 **브로커로 옮긴다.** 브로커는 설정에 고정된 정확히 한 개의 GitLab 기준 주소에만 접속하고, 리다이렉트를 따르지 않으며, http를 허용하는 것은 이 고정 주소(tailnet 안의 주소)뿐이다.
- **토큰 권한:** GitLab **프로젝트 액세스 토큰**, 역할 **Developer**, 범위 `api`(MR 생성에 필요한 최소 범위). Developer는 보호된 브랜치에 직접 push하거나 병합할 수 없다. **전제:** 대상 브랜치(`main`)가 보호되어 있고 병합 권한이 Maintainer 이상이어야 한다. 이 전제는 컷오버 때 사용자가 GitLab에서 확인한다.
- MR 제목과 설명은 서버가 만든다(작업 번호, 요구사항 요약, 서명자, 판정 요약, 해시). **병합은 사용자가 GitLab에서** 직접 한다.
- 새로 저장하는 값: `tasks.branch`, `tasks.mr_iid`, `tasks.mr_url`, `tasks.mr_state`(스키마 v8). `TaskView`에 같이 노출하고 작업 상세에 "MR 열기" 링크(GitLab 주소와 일치하는 URL만 링크로 렌더)를 둔다.

### 4.4 W2b의 새 API 요약
| 메서드·경로 | 등급 | 내용 |
|---|---|---|
| `POST /api/v1/refine/preview` | 쓰기 | 전송될 컨텍스트 목록·크기·제외 내용(전송 없음) |
| `POST /api/v1/refine` | 쓰기 | 브로커 호출, **계획서**(목표 요약, 요구사항 항목, 질문, 범위 밖)를 검증된 JSON으로 반환 |
| `POST /api/v1/tasks/{id}/mr` | 쓰기 | MR 생성 수동 재시도 |
| `TaskView` | | `branch`, `mr_url`, `mr_iid`, `mr_state` 추가 |

## 5. 위협과 대응

| 위협 | 대응 | 남는 위험 |
|---|---|---|
| 탈취된 웹 세션이 작업을 마구 제출 | 주체별 큐 상한 20(전체 100), 쓰기 등급 CSRF, 기록에 주체 남김 | 상한 안에서의 사용량 소모 |
| `orch` 계정 탈취로 키 유출 | 키는 `orch-broker` 소유, `orch`는 읽기 불가 | 브로커의 두 일은 요청 가능(상한으로만 제한) |
| AI 요금 남용 | 시간당·일일 상한, API 쪽 한도, 호출 기록(내용 없음) | 상한 안의 요금 |
| 코드·비밀이 AI로 유출 | 허용 목록(기본 비어 있음, root 설정), 미리보기·확인, 비밀 파일 제외(이중), 크기 상한 | 허용한 저장소의 코드는 외부 API로 나감 |
| 프롬프트 주입(요구사항·코드) | 결과는 검증된 JSON 텍스트, 자동 제출 없음, 에이전트 격리 | 사용자가 속은 제안을 그대로 제출하는 경우 |
| MR로 병합까지 자동 | 토큰은 Developer, `main` 보호가 전제, 병합은 사람 | `main`이 보호되지 않았다면 위험(컷오버 전 확인) |
| MR 스팸 | 브로커가 `orch/<n>` 형식·알려진 작업만 허용, 상한 | 상한 안의 MR 생성 |
| GitLab 토큰 평문 전송(http) | 브로커가 고정된 tailnet 주소에만 접속(WireGuard 구간), 리다이렉트 금지 | tailnet 구간 신뢰 |
| 서명 승인 우회 | 변경 없음. 제출·MR·AI는 승인을 대체하지 못한다 | W1과 같음 |

## 6. 시험·검증 방침

- 모든 신규 쓰기 경로에 W1 방식의 적대 시험: 인증 없음·CSRF 누락·큐 상한·종류 위조·대용량·중복 키.
- W2b는 브로커를 **가짜 API 서버**(OpenAI·GitLab 흉내)로 시험하고, 실제 키는 시험에서 쓰지 않는다. 비밀 파일 제외, 전송 상한, 허용 목록, 호출 상한, 리다이렉트 거부, 고정 주소 외 접속 거부를 변이 시험으로 확인한다.
- OpenAI API의 요청·응답 형식은 구현 시점에 **공식 문서로 확인**한다(구현자가 기억에 의존하지 않는다).
- 컷오버는 W1처럼 단계별로 하고 단계마다 서버에서 본 결과를 기록한다. 실서버에서 확인하지 못한 것은 결과 문서에 "검증 못 함"으로 적는다.
- 웹은 W1과 같은 규칙: 인라인 스크립트·스타일 금지, 모든 서버 문자열은 텍스트 노드로, 위험 API 정적 검사.

## 8. 단계 (계획 문서에서 작업으로 쪼갠다)

**W2a:** A1 스키마 v7(주체 열)과 주체 전달·원장 이벤트 → A2 취소·재시도 오류 코드와 `cancellable`·버그 수정 → A3 제출 검증(종류·큐 상한)과 `GET /repos` → A4 `ops.cloud` 공급과 캐시 → A5 웹: 제출 화면·작업 버튼·`ops` 화면·진행 표시 → A6 적대 시험·결과 문서·컷오버.
**W2b:** B1 브로커 서비스 뼈대(소켓, 설정, 상한, 가짜 서버 시험) → B2 `refine`(컨텍스트 수집·제외·미리보기, API 호출, 스키마 검증) → B3 `create_mr`(GitLab, 고정 주소) → B4 orchd 연동·스키마 v8·`TaskView` → B5 웹: AI 다듬기 화면·MR 링크 → B6 적대 시험·런북·컷오버.

# 서브프로젝트 ② 오케스트레이터 설계서 (초안 v0.1, 2026-11-05)

상위: `06-REQUIREMENTS-orchestrator.md`(승인됨, OR1~OR11), `01-REQUIREMENTS.md`(FR1~FR15), `02-DESIGN-gate.md`(게이트). 양식은 `00-TEMPLATE.md`. **확정**은 사용자가 정한 것, **제안**은 이 문서의 기본안(승인 필요).

## 1. 한눈에 보기

```
 사람 ──Tailscale/ssh──▶ [오케스트레이터 VM]  orchd(Go) + SQLite + aigate + 승인 기록 + 이력 + 쓰기 토큰
                           │  (먼저 거는 쪽은 항상 오케스트레이터)
              ssh(제한 키) │                       │ ssh(제한 키)
                           ▼                       ▼
                    [에이전트 VM]            [검사 VM]
                  Claude/Codex 실행        작업마다 스냅샷 복원
                  로컬 커밋만 함           git 객체만 받아 테스트·빌드 실행
                  (구독 로그인만 보유)      (자격증명 없음)
```
세 VM은 홈서버 OpenStack의 Linux VM이다. 에이전트 VM과 검사 VM은 서로 통신하지 않고 오케스트레이터가 항상 먼저 연결한다.

## 2. 구성 요소 (오케스트레이터 VM)

| 요소 | 역할 | 제안 |
|---|---|---|
| `orchd` | 상시 실행 데몬(Go). 작업 큐, 상태 머신, 단계 실행, 복구 | systemd 서비스 |
| 상태 저장소 | 작업·단계·승인 대기 항목·정책 버전 | SQLite(WAL), 한 파일, 매 단계 전이를 트랜잭션으로 기록 |
| `orch` CLI | 작업 제출(`submit`), 목록(`list`), 상세(`show`), 취소, 승인(`approve`), 승격 제안 보기 | `orchd`의 로컬 HTTP API 클라이언트 |
| `aigate` | 판정·증거·승인 해시·이력(① 그대로). 오케스트레이터 VM에서 실행 | 원격 실행기 추가(4장) |
| 로컬 API | 같은 API를 나중에 웹 화면(FR15)이 쓴다 | 처음엔 `127.0.0.1` 소켓만, 웹은 이후 |
| 비밀 | 저장소 쓰기 토큰, VM ssh 키, 승인·이력 파일 | 오케스트레이터 VM에만 존재 |

## 3. 작업의 일생 (상태 머신)

```
queued ─▶ preparing ─▶ agent_running ─▶ collecting ─▶ verifying ─┬─▶ passed ─▶ publishing ─▶ done
                                                                  ├─▶ needs_approval ─(사람 승인)─▶ verifying(재판정)
                                                                  ├─▶ failed (동작 실패·무력화·불완전)
 어느 단계에서든: cancelled / error(인프라 오류, 재시도 가능)
```

| 상태 | 하는 일 | 실패하면 |
|---|---|---|
| `preparing` | 대상 저장소의 기준 커밋을 `git bundle`로 만들어 에이전트 VM에 전달, 작업 폴더 초기화 | `error`(재시도) |
| `agent_running` | 에이전트 VM에서 고정된 래퍼 명령으로 `claude -p` 또는 `codex exec` 실행, 제한 시간·최대 로그 크기 적용 | 시간 초과는 `failed(incomplete)`, VM 오류는 `error` |
| `collecting` | 에이전트가 만든 **커밋**을 오케스트레이터가 읽기 전용으로 가져옴(5장). 커밋이 없으면 `failed` | `error` |
| `verifying` | 검사 VM을 스냅샷에서 복원하고 `aigate run`을 원격 실행기로 수행(4장) | 판정이 `ok` 아님이면 `failed`/`needs_approval`, 인프라 오류는 `error` |
| `needs_approval` | 승인 대기 항목 생성(승인 해시 포함), 해당 작업만 멈춤. 다른 작업은 계속 | 사람이 `orch approve`로 승인하면 재판정 |
| `publishing` | **허용 목록 안의 행위만** 오케스트레이터가 실행: 작업 브랜치 push, Draft PR, 알림 | 목록 밖 행위는 실행하지 않고 승인 대기 |

- 모든 전이는 SQLite에 기록하고 이력(ledger)에 `task_*` 사건으로도 남긴다(변조 감지).
- `orchd`가 중간에 죽어도 다시 시작하면 마지막 기록된 상태에서 이어간다. 각 단계는 **멱등**하게 만든다(같은 단계를 다시 실행해도 결과가 같음).
- 파괴적 행위(삭제, 운영 서버·권한 변경)는 어떤 상태에서도 코드에서 하드 차단한다. 정책 파일로 풀 수 없다.

## 4. 판정은 샌드박스 밖에서: 원격 실행기

**문제:** 테스트 코드는 검사 VM에서 실행되는 신뢰할 수 없는 코드다. 그 VM 안에서 `aigate`가 판정까지 하면 테스트 코드가 보고서를 위조할 수 있다(요구사항 OR8).

**설계:** `aigate`(판정하는 쪽)는 오케스트레이터 VM에서 돌고, **검사 명령 실행만** 검사 VM에서 한다.
- `runner`에 실행 백엔드를 추가한다: `local`(지금) / `ssh`(검사 VM). `gitx.WithWorktree`도 같은 백엔드로 검사 VM의 베어 저장소에서 worktree를 만든다.
- 검사 결과(JUnit XML, `go test -json`, 종료 코드, 출력 꼬리)는 ssh로 읽어 와서 **오케스트레이터에서 파싱**한다. VM이 돌려준 값은 신뢰하지 않는 입력으로 취급해 크기 상한, 형식 검증, 타임아웃을 건다.
- 판정에 필요한 base/head 트리와 보호 파일 diff, 충돌 검사, 설정 읽기는 모두 **오케스트레이터가 가진 git 객체**로 한다. 검사 VM은 결과 숫자만 돌려준다.
- 환경 변수는 허용 목록으로만 검사 VM에 전달한다(OR3). 검사 VM에는 승인·이력 파일이 없다.
- 이 작업이 ②에서 가장 큰 구현이다. 기존 e2e 시나리오(132개)를 `ssh` 백엔드로도 그대로 돌려 같은 판정이 나오는지 검증한다.

## 5. 에이전트 VM과의 경계

| 방향 | 방법 |
|---|---|
| 코드 전달(오케스트레이터 → 에이전트) | `git bundle`을 ssh로 보내 에이전트 VM에서 푼다. 에이전트 VM은 GitLab에 접속하지 않는다 |
| 에이전트 실행 | 에이전트 VM의 제한된 ssh 키(`command=` 강제)로 래퍼 스크립트(`agent-runner prepare|run|collect`)만 호출 가능 |
| 커밋 회수(에이전트 → 오케스트레이터) | 오케스트레이터가 ssh로 `git fetch`(읽기 전용 `upload-pack`)만 수행. 에이전트 VM이 오케스트레이터로 접속하지 않는다 |
| 로그인 | Claude는 `claude setup-token`의 장기 토큰, Codex는 `codex login --device-auth` 또는 `--with-access-token`을 사용자가 **한 번 직접** 설정한다(CLI 도움말로 옵션 존재 확인, 실제 로그인은 미시험). 토큰은 에이전트 VM 파일 권한 600 |
| 외부 통신 | 방화벽 허용 목록: LLM API 도메인 외 전부 차단. 유출 시도 차단 시험 필요 |

에이전트가 만든 것 중 **git 커밋(객체)만** 오케스트레이터로 넘어온다. 에이전트 VM의 작업 폴더·미추적 파일·git 설정은 이후 단계로 가지 않는다.

## 6. 승인 대기 목록과 승인

- 테이블 `approvals_pending(task_id, kind, hash, base, head, reason, created_at, status)`.
- 종류: `protected_modified`(① 게이트가 요구), `publish_outside_allowlist`, `destructive_blocked`(참고 기록만, 승인 불가).
- 승인은 사람이 오케스트레이터 VM에서 `orch approve <id>`를 실행해 **터미널에서 직접** 한다(Tailscale ssh의 pty로 TTY 요건 충족). 내부적으로 `aigate approve`의 화면·안전 검사를 그대로 쓰고 승인 기록은 오케스트레이터의 `~/.aigate/`에 쌓인다.
- 승인 화면 가독성 개선(한국어 요약, `show`)은 보류 중이던 설계 B안을 이 단계에서 같이 구현한다(FR15의 JSON 보기 모델).
- 에이전트·검사 VM은 승인 기록을 읽거나 쓸 수 없다.

## 7. 정책과 자율 단계

- `policy.yml`(사람이 편집, 오케스트레이터 VM, 버전 해시를 작업마다 기록): 작업 종류별 자율 단계(L0~L3), 허용 목록 행위, 제한 시간, 최대 동시 작업 수.
- 단계별 의미(제안): L0 모든 변경을 사람이 승인 / L1 판정 `ok`면 작업 브랜치에 자동 커밋·push / L2 저위험 종류(문서, 새 테스트 파일)는 승인 필요 항목도 자동 처리하지 않고 알림만 / L3 사후 보고. **하한선(삭제, 운영 서버·권한 변경)은 모든 단계에서 불가.**
- 승격 제안: `orch propose`가 이력의 `stats`(종류별 연속 `ok` 횟수, 승인 필요율, 회귀 발생)로 제안서를 만든다. **승격은 사람이 정책 파일을 바꿔야** 적용된다. 강등은 자동(위반·사고 시 한 단계 하향, 이력에 기록).

## 8. 네트워크와 보안 모델

| VM | 들어오는 연결 | 나가는 연결 |
|---|---|---|
| 오케스트레이터 | 사용자(Tailscale)의 ssh, 이후 웹 | 에이전트 VM·검사 VM ssh, GitLab(읽기·쓰기), 알림 서비스 |
| 에이전트 | 오케스트레이터의 제한 ssh만 | LLM API 도메인만 |
| 검사 | 오케스트레이터의 제한 ssh만 | 패키지 저장소만(Go 프록시, npm, PyPI 등 필요한 것) |

- 모든 VM에 VM 안쪽 방화벽(nftables, 기본 차단)을 둔다. 홈서버 보안그룹은 적용되지 않으므로(확인됨) 의존하지 않는다.
- 위협 모델의 가정: 에이전트 VM의 에이전트는 프롬프트 주입 등으로 악의적으로 행동할 수 있고, 검사 VM의 테스트 코드는 신뢰할 수 없다. 두 VM이 뚫려도 얻을 수 있는 것은 각각 LLM 로그인(제한된 외부 통신 안에서만 사용 가능)과 임시 환경뿐이어야 한다.
- 오케스트레이터 VM이 뚫리면 모든 것이 뚫린다. 그래서 외부 노출 서비스를 두지 않고, 접속은 Tailscale 사용자로 제한하며, 에이전트·검사 VM에서 오케스트레이터로 먼저 거는 경로를 만들지 않는다.
- 알려진 한계: 에이전트 VM의 LLM 로그인 유출, 홈서버 단일 장애(세 VM 모두 같은 장비), OpenStack 하이퍼바이저 탈출은 범위 밖.

## 9. 장애 처리

| 상황 | 처리 |
|---|---|
| 검사 VM·에이전트 VM 접속 불가 | 해당 작업 `error`, 재시도 횟수 상한 후 `failed(incomplete)`. **절대 ok로 처리하지 않음** |
| 스냅샷 복원 실패 | 해당 VM 사용 중지 표시, 작업은 `error`, 알림 |
| `orchd` 재시작 | SQLite의 마지막 상태에서 재개, 멱등 단계 재실행 |
| 에이전트 무한 실행 | 제한 시간 후 강제 종료(원격 프로세스 그룹), 로그 상한 |
| 인프라 오류와 코드 문제 구분 | 인프라 오류는 `error`(재시도), 판정 결과는 `failed` 계열로 분리 |

## 10. 테스트 전략

1. **단위:** 상태 머신 전이 표(허용·금지 전이), 정책 파싱, 허용 목록 판정, 하한선 하드 차단.
2. **원격 실행기:** 기존 e2e 132개를 `ssh` 백엔드로 재실행해 `local`과 판정이 같은지 비교. VM이 거짓 출력(위조 JUnit, 거대 출력, 무한 출력, 형식 깨짐)을 돌려주는 시나리오.
3. **통합(실제 VM):** `sample-collector`로 전 과정(작업 제출 → 에이전트 → 검증 → 승인 대기) 1회.
4. **보안 시험:** 에이전트 VM에서 LAN·오케스트레이터·검사 VM 접속 시도(전부 실패해야 함), 허용 목록 밖 도메인 접속, 승인 파일 읽기 시도, 검사 VM에서 보고서 위조 시도.
5. **장애 주입:** 단계 중간에 VM 중지, `orchd` 강제 종료 후 재개, 스냅샷 복원 실패.

## 12. 가정과 미결정 (`00-TEMPLATE.md` 양식)

**가정(확인 방법)**
- Cinder 스냅샷 복원이 작업 단위로 쓸 만큼 빠르다 → M0에서 측정
- 에이전트 VM에서 Claude/Codex 헤드리스 로그인이 구독으로 동작한다 → M3에서 시험(CLI 옵션 존재는 확인됨)
- ssh 백엔드의 지연(출력·결과 전송)이 판정 시간에 큰 영향을 주지 않는다 → M1에서 측정(현재 35~58초)
- 홈서버에 VM 3개를 올려도 기존 서비스에 영향이 없다 → M0에서 관찰

**미결정(결정자·기본값)**
- 알림 채널(사용자, ⑤에서)
- 에이전트별(Claude, Codex) 동시 실행 수와 토큰 사용 한도(사용자, M3 전, 기본 1건씩 순차)
- 에이전트 VM의 허용 도메인 최종 목록(M3, 실제 동작에 필요한 것만)
- 정책 파일의 작업 종류 분류 체계(M5)

**실험할 것**
- 스냅샷 복원 시간, VM 3개 동시 구동 부하, 방화벽 차단 시험, 원격 실행기 지연, 에이전트 로그인 유지 기간
